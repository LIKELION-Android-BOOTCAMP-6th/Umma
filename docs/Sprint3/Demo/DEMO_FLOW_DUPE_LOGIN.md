# Demo Scenario - FLOW-DUPE-LOGIN

이 문서는 Umma의 `중복 로그인 방지(단일 활성 세션) 데모/QA 기준`이다. (관련 이슈: #366)

V1 중복 로그인 방지 정책은 다음을 전제로 한다.

- 활성 세션의 source of truth는 `서버(Firestore users/{uid}.activeSession)`이다. 로컬에 저장된
  `sessionId`/안내 플래그는 실시간성을 위한 힌트일 뿐이며, 서버와 어긋나면 서버 기준으로 복구한다.
- 같은 계정으로 새 기기가 로그인에 성공하면, 그 직전까지 활성 상태였던 기기는 즉시 강제
  로그아웃된다. 앱이 켜져 있든 꺼져 있든 동일하게 동작해야 한다.
- 강제 로그아웃 안내는 **"즉시 1회, 이후 흔적 없음"** 원칙을 따른다. 안내를 소비하면 로컬 신호는
  즉시 삭제되며, 계정 단위로 영속되는 "밀려남" 기록은 절대 남기지 않는다. 따라서 강제
  로그아웃당한 기기라도 같은 계정으로 언제든 재로그인할 수 있어야 한다(대칭적 재로그인 보장).
- 알림 권한 여부와 무관하게, FCM 토큰이 등록된 기기는 강제 로그아웃 대상에 포함된다.

## 1. 실행 기준

- 동일 계정으로 로그인 가능한 두 대의 기기(A, B)가 필요하다. (에뮬레이터 + 실기기 조합 가능)
- 두 기기 모두 인터넷이 연결되어 있고 FCM 수신이 가능해야 한다.
- 기기 A는 사전에 정상 로그인되어 `users/{uid}.activeSession`이 존재하는 상태여야 한다.
- 강제 로그아웃 시스템 알림 확인을 위해 최소 한 기기는 알림 권한 ON 상태로 준비한다.
- 알림 권한 OFF 상태에서도 강제 로그아웃이 동작하는지 별도로 확인하므로, 권한을 켰다 끌 수 있는
  기기를 하나 포함한다.

데모에서 확인할 핵심은 아래 다섯 가지다.

- 새 기기 로그인 시 서버 `activeSession`이 갱신되고, 이전 기기가 즉시 강제 로그아웃되는지
- 포그라운드/백그라운드 상태에 따라 강제 로그아웃 안내가 적절히(즉시 다이얼로그 / 시스템 알림)
  표시되는지
- 강제 로그아웃당한 기기가 같은 계정으로 재로그인할 때, 안내 흔적 때문에 막히지 않는지(대칭성)
- 신규 설치 기기와 알림 권한 OFF 기기에서도 강제 로그아웃이 누락 없이 동작하는지
- FCM 유실 상황에서 `checkSession()` / 포그라운드 복귀 재검증으로 fallback 처리되는지

---

## 2. 현재 데모 범위

- 포함:
  - 신규 로그인 시 서버 `activeSession.sessionId` 갱신
  - 포그라운드 메인 화면(챗/대시보드/마이페이지)에서의 즉시 강제 로그아웃 + 안내 다이얼로그
  - 백그라운드/종료 상태에서의 시스템 알림(`계정 보안` 채널) + 재진입 시 안내 다이얼로그 1회
  - 강제 로그아웃 후 동일 계정 재로그인(대칭적 재로그인, 흔적 없음)
  - 강제 로그아웃 안내의 TTL(5분) 만료 후 미노출
  - 신규 설치 기기의 즉시 알림 디바이스 등록
  - 알림 권한 OFF 기기에서의 강제 로그아웃 수신
  - 포그라운드 복귀(`onStart`) 시 서버 세션 재검증
  - claimSession 실패로 인한 자기 자신 오탐 로그아웃 방지
- 제외:
  - 3대 이상 기기 동시 로그인 시나리오(2대 기준으로만 검증)
  - 워치(Wear OS) 측 세션 정책
  - 관리자/백오피스에서의 강제 세션 만료 기능

## 3. 데모 시나리오

### 시나리오 1 - 새 기기 로그인 시 서버 activeSession 갱신

1. 기기 A로 계정 X에 로그인된 상태를 준비한다.
2. Firestore `users/{X}.activeSession`을 확인하여 `deviceId=A`, `sessionId`가 기록되어 있는지
   확인한다.
3. 기기 B에서 동일 계정 X로 Google 로그인한다.
4. 로그인 직후 Firestore `users/{X}.activeSession`을 다시 확인한다.

기대 결과:

- `activeSession.deviceId`가 B로, `sessionId`가 새 값으로 갱신된다.
- B의 로컬 `active_session_id`에도 동일한 `sessionId`가 저장된다(`claimSession()` 성공).

---

### 시나리오 2 - 포그라운드 즉시 강제 로그아웃

1. 시나리오 1 진행 직전, 기기 A를 챗/대시보드/마이페이지 등 메인 화면에 띄워 둔다.
2. 기기 B에서 계정 X로 로그인한다.
3. 기기 A 화면을 관찰한다(별도 조작 없이).

기대 결과:

- 기기 A는 **앱 재시작 없이** 즉시 강제 로그아웃되어 인증 그래프(로그인/온보딩) 화면으로
  이동한다.
- "다른 기기에서 로그인되어 자동으로 로그아웃되었습니다" 안내 다이얼로그가 표시된다.
- "확인"을 누르면 다이얼로그가 닫히고 정상적으로 로그인/온보딩 화면이 표시된다.

---

### 시나리오 3 - 백그라운드 강제 로그아웃 + 시스템 알림

1. 기기 A에서 계정 X로 로그인된 상태에서 앱을 백그라운드로 보낸다(홈 버튼).
2. 기기 B에서 계정 X로 로그인한다.
3. 기기 A의 알림 영역을 확인한다.
4. 기기 A 앱을 다시 연다.

기대 결과:

- 기기 A에 `계정 보안` 채널로 "다른 기기에서 로그인되었습니다" 시스템 알림이 표시된다(알림
  권한 ON인 경우).
- 앱을 다시 열면 인증 그래프로 이동되어 있고, 안내 다이얼로그가 1회 표시된다.
- 다이얼로그를 닫은 뒤 다시 진입해도 동일 안내가 재표시되지 않는다.

---

### 시나리오 4 - 대칭적 재로그인 (흔적 없음)

1. 시나리오 2 또는 3을 통해 기기 A가 강제 로그아웃된 상태를 만든다.
2. 기기 A에서 **동일 계정 X로 즉시 재로그인**한다.
3. 기기 B의 화면을 관찰한다.

기대 결과:

- 기기 A는 강제 로그아웃 안내 없이 정상적으로 로그인/대시보드에 진입한다(과거 "밀려남" 기록이
  재로그인을 막지 않음).
- 이번에는 **기기 B**가 시나리오 2/3과 동일한 프로세스로 강제 로그아웃된다.
- Firestore `activeSession.deviceId`가 다시 A로 갱신된다.

---

### 시나리오 5 - 강제 로그아웃 안내 TTL 만료

1. 기기 A를 강제 로그아웃시킨다(시나리오 2/3).
2. 안내 다이얼로그가 뜨기 전, **5분 이상 경과**할 때까지 기다린다(또는 디버그 빌드에서 TTL을
   단축해 재현).
3. 그 이후에 기기 A 앱을 (재)실행한다.

기대 결과:

- 5분이 지난 뒤에는 강제 로그아웃 안내 다이얼로그가 표시되지 않는다.
- 로컬 안내 신호는 소비 시점에 즉시 삭제되어 이후 무관한 로그인 시점에 재노출되지 않는다.

---

### 시나리오 6 - 신규 설치 기기의 즉시 등록

1. 계정 X로 로그인된 적 없는 새 기기(또는 앱 데이터 초기화) C를 준비한다.
2. 기기 C에서 계정 X로 처음 로그인한다.
3. Firestore `users/{X}/notification_devices/{C의 deviceId}`를 확인한다.
4. 기기 C가 메인 화면에 떠 있는 상태에서, 다른 기기(A 또는 B)로 계정 X에 로그인한다.

기대 결과:

- 로그인 직후(앱 재시작 없이) `notification_devices/{C}` 문서에 `fcmToken`이 채워진다.
- 다른 기기 로그인 시 기기 C도 즉시 강제 로그아웃 대상에 포함되어 시나리오 2와 동일하게
  동작한다.

---

### 시나리오 7 - 알림 권한 OFF 기기에서의 강제 로그아웃

1. 기기 A에서 계정 X로 로그인한 뒤, 시스템 설정에서 알림 권한을 OFF한다.
2. Firestore `users/{X}/notification_devices/{A}`에서 `fcmToken`이 유지되고
   `permissionGranted=false`인지 확인한다.
3. 기기 B에서 계정 X로 로그인한다.

기대 결과:

- 기기 A는 알림 권한이 없어도 `force_logout` FCM을 수신하여 정상적으로 강제 로그아웃된다(시스템
  알림만 표시되지 않음).
- 동일 권한 상태에서 SRS 복습/마케팅 알림은 여전히 발송되지 않는다(회귀 없음).

---

### 시나리오 8 - 포그라운드 복귀 시 서버 재검증 (FCM 유실 대비)

1. 기기 A에서 계정 X로 로그인 후 메인 화면에 둔다.
2. 기기 A의 네트워크를 일시적으로 차단하거나 FCM 수신을 막은 상태에서, 기기 B로 계정 X에
   로그인한다.
3. 기기 A의 네트워크를 복구한 뒤, 앱을 백그라운드로 보냈다가 다시 포그라운드로 전환한다
   (`onStart` 트리거).

기대 결과:

- FCM을 받지 못했더라도, 포그라운드 복귀 시점에 서버 `activeSession`과 로컬 세션을 재검증하여
  불일치가 감지되면 강제 로그아웃 + 안내가 처리된다.

---

## 4. 예외 시나리오

### 시나리오 9 - claimSession 실패 시 자기 자신 오탐 방지

1. (디버그 환경) `claimLoginSession` 호출이 실패하도록 네트워크/함수 오류를 재현한 상태에서 기기
   A로 새로 로그인한다.
2. 로컬 `active_session_id`가 비어 있는 상태에서 `checkSession()` 또는 `onStart` 재검증이
   수행되도록 한다.

기대 결과:

- 로컬 `sessionId`가 없다는 이유로 방금 로그인한 기기 A 자신이 강제 로그아웃되지 않는다.
- 내부적으로 재`claimSession()`이 시도되며, 성공 시 정상 상태로 복구된다.
- 재시도도 실패하면 기존 로그인 상태를 유지한 채 다음 기회에 다시 시도한다(무한 로그아웃 루프
  없음).

---

### 시나리오 10 - 최초 로그인(활성 세션 없음)

1. `activeSession` 필드가 없는 계정(레거시 사용자 또는 최초 사용자)으로 기기 A에서 로그인한다.

기대 결과:

- 로그인한 기기 자신은 broadcast 대상에서 서버 측에서 제외되므로 강제 로그아웃되지 않는다.
- `activeSession`이 새로 생성되고 정상적으로 진입된다.

## 6. 합격 기준

- 새 기기 로그인 시 서버 `activeSession`이 항상 최신 로그인 기기 기준으로 갱신된다.
- 이전 활성 기기는 앱 상태(포그라운드/백그라운드/종료)와 무관하게 강제 로그아웃된다.
- 강제 로그아웃 안내는 즉시 1회만 표시되고, 이후 어떤 흔적도 남기지 않아 동일 계정으로의
  재로그인을 막지 않는다(대칭적 재로그인 보장).
- 알림 권한 여부, 신규 설치 여부와 무관하게 강제 로그아웃 broadcast 대상에서 누락되는 기기가
  없다.
- FCM 유실 시에도 `checkSession()`/포그라운드 재검증을 통해 최종적으로 세션 일관성이
  복구된다.
- claimSession 실패 등 일시적 오류로 인해 정상 로그인한 기기 자신이 오탐 로그아웃되지 않는다.
