# Demo Scenario - FLOW-WATCH-NOTIFICATION

이 문서는 Umma Wear OS Companion V1의 `워치 알림 데모/QA 기준`이다.

V1 알림 정책은 다음을 전제로 한다.

- 알림의 source of truth는 `폰`이다.
- 알림 생성은 기존 폰 FCM/로컬 알림 경로를 사용한다.
- 워치는 시스템 notification mirroring으로 알림을 받는다.
- V1에서 워치 자체 FCM token 등록 및 direct watch push는 구현하지 않는다.
- 워치 액션은 `SRS 알림`에만 우선 제공한다.

## 1. 실행 기준

- 폰 앱은 로그인된 상태여야 한다.
- 폰의 알림 권한은 허용 상태여야 한다.
- 워치는 폰과 페어링되어 있어야 한다.
- 폰과 워치 모두 네트워크 연결이 가능해야 한다.
- V1 기준 워치 알림은 `폰에서 생성된 알림이 워치로 미러링되는지`를 검증한다.

데모에서 확인할 핵심은 아래 세 가지다.

- 워치에서 SRS 알림이 정상적으로 보이는지
- 워치 액션이 폰의 기존 notification/use case 흐름으로 안전하게 연결되는지
- `워치에서 복습 / 10분 뒤 다시 알림 / 폰에서 열기`가 중복 없이 동작하는지

---

## 2. 현재 데모 범위

- 포함:
  - SRS 알림 미러링
  - 워치 알림 액션
  - 폰 handoff
  - snooze 재스케줄
- 제외:
  - 마케팅 알림 전용 워치 UX
  - watch direct push
  - watch token registration
  - Tile/Complication

## 3. 데모 시나리오

### 시나리오 1 - SRS 알림 미러링 수신

1. 폰에서 SRS 알림이 생성되도록 due flashcard 상태를 준비한다.
2. 폰에 SRS 알림이 표시되는지 확인한다.
3. 같은 알림이 워치에 미러링되어 표시되는지 확인한다.
4. 워치 알림 제목/본문이 과도하게 길지 않고 한눈에 읽히는지 확인한다.

기대 결과:

- 워치가 direct push 없이도 폰 알림을 동일한 logical event로 보여준다.
- 워치 알림 본문은 짧고 절삭된 형태로 노출된다.
- 민감한 전체 transcript나 불필요한 상세 데이터는 노출되지 않는다.

---

### 시나리오 2 - `워치에서 복습` 액션

1. 워치에서 SRS 알림을 연다.
2. `워치에서 복습` 액션을 탭한다.
3. 워치 앱이 review entry 화면으로 진입하는지 확인한다.
4. 폰에서는 별도의 중복 진입이 발생하지 않는지 확인한다.
5. due card가 존재하면 첫 review 상태가 준비되는지 확인한다.

기대 결과:

- 워치 액션이 phone-owned command 경로로 전달된다.
- 워치 앱이 짧은 복습 진입점으로 열린다.
- 같은 알림을 기준으로 폰과 워치가 중복 네비게이션을 발생시키지 않는다.

---

### 시나리오 3 - `10분 뒤 다시 알림` 액션

1. 워치에서 SRS 알림을 연다.
2. `10분 뒤 다시 알림` 액션을 탭한다.
3. 현재 알림이 닫히는지 확인한다.
4. 폰이 snooze command를 받아 재스케줄하는지 확인한다.
5. 약속된 시점에 동일한 종류의 알림이 다시 오는지 확인한다.

기대 결과:

- snooze action은 워치가 아닌 폰이 최종 처리한다.
- 기존 알림이 반복 노출되지 않는다.
- 재알림은 새 logical event가 아니라 기존 리마인더 흐름의 연장으로 동작한다.

---

### 시나리오 4 - `폰에서 열기` 액션

1. 워치에서 SRS 알림을 연다.
2. `폰에서 열기` 액션을 탭한다.
3. 폰이 켜지거나 포그라운드로 복귀하는지 확인한다.
4. 의도한 route로 이동하는지 확인한다.
5. 워치 쪽에서는 action 완료 후 별도 오류 없이 대기 상태로 돌아가는지 확인한다.

기대 결과:

- 폰이 현재 SRS route 또는 handoff route로 정확히 열린다.
- 기존 앱 백스택을 깨지 않고 재사용 가능하면 재사용한다.
- 워치와 폰이 동시에 두 개의 독립 리뷰 세션을 만들지 않는다.

---

### 시나리오 5 - due card 없음 상태

1. 워치 알림이 도착한 뒤, 폰에서 먼저 review를 완료하거나 due card를 소진한다.
2. 이후 워치에서 늦게 `워치에서 복습` 액션을 누른다.
3. 워치에서 empty review 상태 또는 안내 문구가 보이는지 확인한다.
4. `폰에서 열기` CTA가 필요하면 제공되는지 확인한다.

기대 결과:

- 오래된 알림 액션을 눌러도 crash가 나지 않는다.
- due card 없음 상태가 사용자에게 명확히 보인다.
- review 진입 실패가 아니라 empty state로 처리된다.

---

## 4. 예외 시나리오

### 시나리오 6 - 알림 권한 거부

1. 폰의 POST_NOTIFICATIONS 권한을 거부한다.
2. SRS 조건을 만족시킨다.
3. 폰과 워치 모두 알림이 뜨지 않는지 확인한다.

기대 결과:

- 권한이 없는 상태에서 워치 미러링도 발생하지 않는다.
- 앱은 권한 안내 또는 설정 유도 흐름으로 복구할 수 있어야 한다.

---

### 시나리오 7 - 폰 미연결 상태에서 워치 액션

1. 알림은 이미 워치에 떠 있는 상태에서 폰 연결을 끊는다.
2. 워치에서 `워치에서 복습` 또는 `10분 뒤 다시 알림`을 누른다.
3. action 처리 실패 또는 재연결 필요 상태가 보이는지 확인한다.

기대 결과:

- direct cloud fallback을 시도하지 않는다.
- 사용자는 `폰 연결 필요` 또는 유사한 복구 안내를 받는다.

## 6. 합격 기준

- 폰이 알림 SSOT로 유지된다.
- 워치가 direct push 없이 SRS 알림을 안정적으로 수신한다.
- 세 개의 워치 액션이 모두 폰 중심 흐름에 연결된다.
- 오래된 액션, due card 없음, 연결 끊김 같은 예외 상황에서도 crash 없이 복구 가능하다.
- 워치 알림 본문이 과도한 개인정보를 노출하지 않는다.
